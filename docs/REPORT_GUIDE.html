How a run works

One POST /analyze drives seven steps. The host, a .NET program, owns every step; the model is consulted in steps 4 and 5 only, and nothing a model says can change the facts recorded in steps 1 to 3 or measured in step 6.

FingerprintSHA-256 of every tracked file in the repository under review, plus the commit and dirty flag.
GraphGraphify builds a code graph for exactly this fingerprint, or reuses the published one.
Static analysisThe repository is built with the SecureYourCode Roslyn analyzer; its PERF* warnings become baseline candidates.
SpecialistsThree reviewer agents (Memory, CPU, Concurrency) read code and the graph, explain the baseline candidates and may add their own findings.
CriticA fourth agent challenges every candidate: keep, downgrade or remove, and may propose a benchmark from a fixed list.
VerificationThe host runs its own benchmark programs against the code and measures. No model-written code ever runs.
ReportStatus, provenance, usage, findings. Written as JSON and as this HTML, both at once or neither.

Every agent runs inside the Copilot engine, a local process, with read-only tools: it may view, grep and glob files inside the repository and query Graphify. Writes, shell commands and web access are refused by the host's permission handler, and refusals are counted in the report.

Run block

Run
The run ID: UTC date and time of the start plus four random hex characters. The report folder under .secureyourcode\reports carries the same ID.
Run status
Describes the analysis, never the writing of the report. Three values, decided by fixed rules in host code:
  • complete: static analysis produced valid results, all three specialists and the critic returned valid, complete answers, and none of the partial conditions occurred.
  • partial: the run finished, but the source changed during it, a specialist failed after one repair attempt, the critic failed or left decisions missing, or the benchmark infrastructure itself failed. The reason is printed next to the status.
  • failed: the build for static analysis failed, the agent engine could not start, or the 30-minute limit or a cancellation stopped the run before the specialists finished. The report is still written with whatever completed.
This run: complete.
Graph status
Separate from run status. current: the graph was built from exactly the fingerprint analysed. stale: an older graph was used and labelled. none: no graph, so the reviewers ran without Graphify. A run can be complete with a stale graph; a banner would say so. This run: current.
Started / Finished
UTC timestamps. This run took 89 seconds for all seven steps, including two benchmark builds.
Models used
The model names the engine reported in its usage events, one entry per distinct model. In Copilot mode this can vary per call because GitHub routes "auto"; in ApiKey mode it is the single model name configured for your endpoint.

Provenance

Provenance answers "which code, exactly, and through which model backend". It exists so a finding can never be mistaken for a statement about some other version of the code.

LLM backend
Which of the two modes ran. Copilot (model …) means GitHub's hosted service with a developer's sign-in. ApiKey (openai endpoint …, model …) means your own OpenAI-compatible endpoint; the key itself is never shown or stored in the report.
Commit
The git commit of the repository under review at the start of the run.
Dirty working tree
yes when the working tree had uncommitted changes. In this run it was yes because Husky's tool manifest and hook files had been installed by hand into the demo repository before the first start, and the host only commits the files its own installer writes. The fingerprint covers the working tree as it was, so the analysis is still exact; the flag just tells you the commit alone does not describe what was analysed.
Source fingerprint
SHA-256 over every tracked and untracked, non-ignored file's path and content. It is recomputed after the graph stage, before verification, around every benchmark and at the end of the run. Any change at any of those points downgrades or discards results. This is the mechanism behind every E2.
Graph built from fingerprint
The fingerprint the Graphify graph was extracted from. Equal to the source fingerprint here, which is what current means.

Token usage

One row per agent session plus a total. Each row is exact, summed from the engine's per-call usage events.

Model calls
How many times the agent went to the model within its session. A high count means a long tool-using conversation: in this run MemoryReviewer made 23 calls while reading files and querying Graphify, VerificationReviewer 12, and CpuReviewer and ConcurrencyReviewer one call each.
Input / Output tokens
Summed over the calls. Input is large because every call re-sends the conversation so far, including file contents the agent viewed. A field no call reported would read "not reported", never 0.
Cost
In Copilot mode this is GitHub's "premium request cost units", never money. In ApiKey mode the column reads not applicable (ApiKey mode): your endpoint has no such accounting, and the engine's placeholder value of 0 must not be shown as a real measurement.

The 23 versus 1 difference is the most informative number in this block. One call means the agent answered from the prompt alone, enriching the analyzer's candidates without opening a file. See what to say honestly.

Reviewers table

Reviewer
The four agents: MemoryReviewer, CpuReviewer, ConcurrencyReviewer (the specialists, one pillar each) and VerificationReviewer (the critic).
Status
completed means the agent returned valid JSON in the required schema, possibly after one repair request. Other values, failed or not_run, make the run partial or failed.
Graphify
available, N calls: the Graphify MCP server was offered to the session and the agent used its tools N times successfully. Here Memory used it 4 times; the other three had it available and chose not to use it.
Denied tool requests
How often the host refused an action: a read outside the repository, a write, a shell command, a web fetch, or a Graphify call with a disallowed argument. Zero across the board here. A non-zero value is not an error; it shows the guard rails working.
Notes
Diagnostics the host recorded about that agent's output: discarded findings and why, identity mismatches, ignored benchmark proposals. Empty in this run.

Anatomy of a finding

Findings are grouped by category. Each card has a header line and a field list. Who writes each field matters, so the owner is marked.

Header line

Example: E2 Roslyn confidence: candidate PERF004 Services/ReportCache.cs:28 — ReportCache.GetOrAdd. That is the evidence badge, the origin label, the confidence label, then rule ID, file and line, and the enclosing symbol.

OriginhostRoslyn analyzer: the finding started as a compiler diagnostic. AI specialist (…): a model proposed it and the host validated its location.

MechanismreviewerWhat grows or repeats and why. Prose from a specialist; for an unenriched candidate it reads "not analyzed by a specialist".

Evidence vs. confidence

These are two different axes, assigned by different parties, and the report prints both because neither replaces the other.

Evidence says what was proven mechanically, and the host assigns it from facts it gathered itself. Confidence says how sure the reviewers are, and only models set or change it. A finding can have strong proof and a modest confidence label, as every E2 in this run does.

Evidence levels

LevelMeaningThe host assigns it whenModel calls involved
E0AI hypothesisThe finding came from a specialist and exists only because a model argued for it. The host validated that the file, lines and symbol are real, but the mechanism is the model's claim.Yes, the specialist's own
E1Deterministic compiler evidenceThe finding is a PERF* warning from the SecureYourCode Roslyn analyzer, produced by building the repository while the fingerprint equalled the one being analysed. The compiler found the pattern in the syntax and semantic model. Nothing else earns E1.None
E2Independently reproducedA host-owned benchmark program ran against the code at the finding's exact method, each of three input sizes in a fresh process, every measurement validated, and the template's acceptance rule held, with the fingerprint unchanged before, during and after.None

Why E1 and E2 need no model call

E1 is the compiler speaking. The analyzer's three rules look for specific code shapes: a query-executing call inside a loop (PERF001), Task.WhenAll over an input-sized collection (PERF003), growth of a static collection with no removal anywhere in the type (PERF004). A warning either fires or it does not; there is no judgement to delegate. The host records the warning as a baseline candidate before any agent starts, and a model can later explain it but can never remove, relabel or move it.

E2 is a measurement. The host copies a small benchmark program of its own, points it at the repository, builds it once, and runs it three times with n = 10, 100 and 1000, each time in a new process so nothing carries over. Each process prints one number. The host checks the numbers against a rule fixed in code. The model's only role is upstream: the critic may propose that a benchmark be run, by naming a kind and scenario from a fixed list, and the host decides whether that proposal is even applicable. For the P1 seam the host runs the benchmark automatically, proposal or not.

Confidence labels

LabelWho sets itMeaning
candidatehost defaultEvery Roslyn baseline candidate starts here: the analyzer saw the pattern, nobody has vouched for it further. A specialist may leave it as is.
stronga specialistThe specialist read the code and is confident the mechanism is real. When several specialists touch the same candidate, the higher confidence wins.
lowthe criticSet by a downgrade decision. The finding moves to the "Low-confidence candidates" section. Evidence is untouched: a downgraded E1 stays E1.

So in this run the two E2 findings say confidence: candidate for a simple reason: CpuReviewer and ConcurrencyReviewer enriched them in one model call each and did not raise the label, and the critic kept them without changing it. Meanwhile the host measured N+1 repository calls and unbounded cache growth directly. If someone asks which to believe, the answer is that E2 is the stronger statement: it is a reproduced measurement, while the confidence label is an opinion the reviewers happened not to upgrade. The one strong label in the run belongs to the E0 finding, which is exactly the opposite case: a confident model with no mechanical proof yet.

Benchmarks and E2

Three benchmark templates exist, each bound to one method of the demo project, called its seam. A template can only ever verify the code it was written for; seam matching compares type and method name, which is what stops the P1 benchmark from marking P5, another PERF001 in a different method, as E2.

TemplateSeamMeasuresAcceptance rule for E2When it runs
RepositoryCallAmplification / OrderCustomerLookupOrderSummaryService.BuildSummariesAsyncRepository calls made for n orders with distinct customersvalue(n) ≥ 0.9·n for every n, and value(1000) ≥ 50·value(10)Automatically for every PERF001 at this seam not removed by the critic
CollectionGrowth / ReportCacheReportCache.GetOrAddEntries retained in the static cache after n distinct keys and a forced full garbage collectionvalue(n) ≥ 0.9·n for every nOnly when the critic proposes it for a kept candidate at this seam
TaskFanOut / NotificationRecipientsNotificationService.NotifyAllAsyncTasks started for one call with n recipientsvalue(n) ≥ 0.9·n for every nOnly when the critic proposes it for a kept candidate at this seam

Reading "n=10: 10, n=100: 100, n=1000: 1000"

For P1 this reads: 10 orders caused 10 repository calls, 100 caused 100, 1000 caused 1000. One call per order is the N+1 pattern the analyzer suspected, now measured. The second clause of the rule, value(1000) ≥ 50·value(10), rules out a fixed overhead that happens to be large. For P3 it reads: after inserting 10, 100 and 1000 distinct keys and forcing a full garbage collection, the cache still held 10, 100 and 1000 entries. Nothing was ever evicted, so memory grows with the number of distinct keys for the life of the process.

Why fresh processes

The cache is static. If the three sizes ran in one process the counts would pile up (10, then 110, then 1110) and prove nothing about any single size. A fresh process per n makes the three values independent. The 3-minute benchmark budget covers the build and all three processes.

Source binding

E2 must prove the same source state that produced the finding. The fingerprint is recomputed before verification starts, before and after each benchmark, and at the end of the run. A mismatch at any point discards that benchmark's result or, at the end, reverts every E2 of the run to its previous level and marks the run partial / source_changed. No E2 in a complete run can refer to code that moved under it.

Critic decisions

The critic must challenge every candidate and look for counter-evidence about the same mechanism, for example a cache that is actually bounded elsewhere, or a loop whose repository already batches. Exactly one decision per candidate is required; the host asks once for a repair if any is missing, and marks any still missing as "not reviewed by critic" while making the run partial.

DecisionWhere the finding goesConfidenceEvidenceCounted in the metrics
keepIts category sectionAs reportedUnchangedYes
downgrade"Low-confidence candidates"Set to lowUnchangedYes

The critic may also propose at most two benchmarks, for kept candidates only, by naming a kind and scenario from the table above. It never writes code. A proposal whose pair is not in the table, or whose candidate is not at that template's seam, is ignored and noted in the report. In this run the critic proposed both optional benchmarks that apply to the demo, and both were accepted; the Notes block records that.

Notes block

Free-text notes the host adds about the run as a whole. The three in this report:

  • Benchmark proposal accepted: RepositoryCallAmplification/OrderCustomerLookup for d36b9de2871f. The critic's proposal matched a template and a seam, so the host ran it. For this template the run would have happened anyway, since it is required for its seam.
  • Benchmark proposal accepted: CollectionGrowth/ReportCache for 059d11969b52. The optional benchmark that gave P3 its E2.
  • E2 means verified by a host-owned benchmark template bound to a demo seam; in the hackathon it applies to the demo project only. A deliberate scope statement. Three templates exist and they know three methods of the demo project. Any other repository gets E0 and E1 only until templates are written for its seams.

What the report leaves out, on purpose

  • No overall score and no severity. The plan forbids both. A single number would hide the difference between a measured fact and a hypothesis; the evidence badge and the confidence label carry that information separately.
  • No remediation written by the host. Every fix direction is a reviewer's sentence, attributed as such. The host never invents advice.
  • No confirmed-leak language without E2. Analyzer messages say "potential". Only a verified benchmark earns stronger wording, and even then the report says what was measured rather than drawing the conclusion for you.
  • No trust in any dynamic string. Every value a model or the repository supplied is HTML-encoded in the page, so a <script> copied from a source comment appears as text.

Air-gapped specifics

This run used ApiKey mode: the same agent engine, prompts, tools and permission handler as in Copilot mode, but with every model request sent to the company's own OpenAI-compatible endpoint with an API key. No GitHub account, no Copilot subscription and no traffic outside the company network were involved. Three lines in the report show it:

  • LLM backend names the mode, the endpoint and the model, never the key.
  • Models used is the single internal model name, since there is no routing between models.
  • Cost reads "not applicable (ApiKey mode)" throughout.

The run also settled the one question that could not be tested outside the network: the internal model handles OpenAI-style function calling well enough for the agents to read files and query the graph. MemoryReviewer's 23 calls, 4 of them Graphify queries, and its discovery of P4 are the proof.

What to say honestly

One run. Precision and recall of 1.0 come from a single complete run on the demo project. Model output varies between runs; the plan records metrics from one run by design and says so.

Two specialists did not use their tools. CpuReviewer and ConcurrencyReviewer answered in one model call each with no file reads and no Graphify queries. Their findings were correct because the analyzer had already located them; their "execution path" text is partly inferred, for example the method name NotifyAsync(r). On a larger repository this behaviour would matter more. The prompts were deliberately not tuned against the known answers.

E2 is scoped to the demo seams. The three benchmark templates verify three known methods. This is a demonstration of the mechanism, not a general verifier.

P2 reached E1, not E2, this time. The optional TaskFanOut benchmark depends on a critic proposal, and the critic spent its two proposals on P1 and P3.

Dirty working tree. Caused by the manual Husky installation in the demo repository, not by the analysis. The fingerprint still describes the analysed files exactly.

Glossary

Baseline candidate
A finding created by the host from an analyzer warning before any agent runs. Its identity fields can never be changed by a model.
Enrichment
A specialist filling in mechanism, trigger, execution path, confidence and fix direction on a baseline candidate. Nothing else.
LLM-only finding
A finding a specialist proposed that matches no analyzer warning. The host checks the file exists in the repository, the lines are valid, recomputes the enclosing symbol itself, and requires an LLM-* rule ID. It becomes an E0 candidate or is discarded with a recorded reason.
Graphify
A code-graph tool. The host extracts a graph of the repository per commit and offers four read-only query tools to the agents through the Model Context Protocol.
Seam
A public method of the demo project that a benchmark template is written against.
Fingerprint
SHA-256 over all tracked and untracked non-ignored files. The identity of the source state; see Provenance.
Fresh process
Each benchmark size runs in its own newly started process so static state cannot leak between measurements.
Denied tool request
An agent action the host's permission handler refused. Counted per agent in the Reviewers table.
Premium request cost units
GitHub Copilot's accounting unit for model calls. Not money, and not applicable to a self-hosted endpoint.
